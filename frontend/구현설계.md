## 2. 기능별 분리

### 2.1 API 통신 레이어 (`api/`)

**책임**: 백엔드와의 HTTP 통신만 담당, UI 로직 전혀 모름.

```ts
// api/client.ts
const BASE_URL = import.meta.env.VITE_API_BASE_URL;

async function apiFetch<T>(path: string, init?: RequestInit): Promise<T> {
  const res = await fetch(`${BASE_URL}${path}`, init);
  if (!res.ok) {
    const body = await res.json().catch(() => null);
    throw new ApiError(res.status, body?.error?.code, body?.error?.message);
  }
  return res.status === 204 ? (undefined as T) : res.json();
}

export class ApiError extends Error {
  constructor(public status: number, public code?: string, message?: string) {
    super(message ?? `요청 실패 (${status})`);
  }
}
```

```ts
// api/presentations.ts
export function createPresentation(body: { title: string; script: string | null }) { ... }
export function submitPresentation(id: number, token: string, body: { audio_duration_ms: number }) { ... }
export function getPresentation(id: number, token: string) { ... }
export function uploadToPresignedUrl(url: string, file: File) {
  return fetch(url, { method: "PUT", body: file }); // 백엔드 안 거침, BASE_URL 아님
}
```

에러 코드(`PRESENTATION_EXPIRED`, `PRESENTATION_NOT_FOUND`, `AUDIO_DURATION_EXCEEDED` 등)는 `ApiError.code`로 각 화면에서 분기.

⚠️ **403(토큰 불일치)과 404(존재하지 않는 id)는 `error.code`가 둘 다 `"PRESENTATION_NOT_FOUND"`로 동일하다** (`PresentationErrorCode` 참고 — 코드 문자열은 같고 HTTP status만 다름). 그러니 이 둘을 구분할 땐 반드시 `ApiError.status`(403 vs 404)로 분기하고, `code` 문자열로 구분하려 하면 안 됨.

### 2.2 타입 (`types/`)

API 명세서 §2.1~§2.3.1을 그대로 TS 인터페이스로. `report.ts`는 ai-service `AnalysisReport`(`app/schemas/report.py`) 트리와 1:1 대응시켜서, 나중에 스키마 바뀌면 여기만 보면 되게.

⚠️ **`filler.type`은 4개가 아니라 11개다**: `음`·`어`·`그`·`저`·`뭐`·`뭔가`·`좀`·`막`·`그냥`·`같다`·`기타` (2026-09-07 확장, `report.py`의 `FillerType` 참고). 유니온 타입 만들 때 이 11개 전부 포함할 것.

### 2.3 세션 관리 (`session/`)

**책임**: STEP 1→2→3 사이에 들고 다녀야 하는 값(`presentation_id`, `result_token`, presigned URL들) 보관.

- `sessionStorage` 기반 — 새로고침엔 살아남고 탭 닫으면 사라짐(민감정보라 localStorage보다 적절)
- `/r/:id` 리포트 화면은 URL 쿼리(`?token=`)가 우선 — 공유 링크로 새 탭에서 들어올 수도 있으니 sessionStorage에 의존하면 안 됨

```ts
// session/usePresentationSession.ts
type Session = {
  presentationId: number;
  resultToken: string;
  slideUploadUrl: string;
  audioUploadUrl: string;
};
// setSession/getSession/clearSession — sessionStorage.getItem/setItem 래핑
```

### 2.4 STEP 1 — `features/create/`

- `CreateScreen.tsx`: 제목 입력 + 접힌 스크립트 textarea + "다음" 버튼
- 제출 시: `createPresentation()` → 성공하면 `session/`에 저장 → `navigate("/upload")`
- 로딩/에러 상태는 컴포넌트 로컬 `useState`로 충분 (전역 상태 불필요)

### 2.5 STEP 2 — `features/upload/`

- `UploadCard.tsx`: PPT/오디오 공용, `status: 'empty' | 'uploading' | 'done' | 'error'` prop으로 테두리색 결정
- `useFileUpload.ts`: 파일 선택 → `uploadToPresignedUrl()` 호출 → 진행 상태 반환. 오디오는 업로드 전에 `<audio>` 엘리먼트나 Web Audio API로 `duration` 측정해서 같이 보관(submit에 필요)
- 오디오 포맷 제약 없음 — 백엔드가 S3 키를 무조건 `audio.webm`으로 고정하지만 실제 처리(ai-service librosa)는 내용 기반으로 포맷 자동 인식이라 mp3/m4a/webm 등 아무 포맷이나 그대로 PUT하면 됨(변환 불필요, m4a로 실측 검증됨)
- `UploadScreen.tsx`: 두 카드 상태를 모아서 "분석 시작하기" 활성화 여부 계산, 클릭 시 `submitPresentation()` → `navigate("/r/:id?token=...")`

### 2.6 STEP 3 — `features/report/`

- `usePollReport.ts`: `setInterval` 2~3초로 `getPresentation()` 호출, `status`가 DONE/FAILED면 폴링 중단
- `ReportScreen.tsx`: 폴링 상태에 따라 분기
  - PROCESSING → 로딩 UI
  - DONE → `report`를 하위 섹션 컴포넌트들에 분배
  - FAILED → `error.code`별 메시지
  - `ApiError.status === 403 | 410` → 별도 안내 화면(권한없음/만료)
- `ConsistencySection.tsx` / `DeliverySection.tsx` / `ScriptDiffSection.tsx`: 리포트 하위 트리 하나씩 전담, `report.script_diff`가 `null`이면 `ScriptDiffSection` 자체를 렌더링 안 함

### 2.7 라우팅 (`router.tsx`)

```
/            → CreateScreen (STEP 1)
/upload      → UploadScreen (STEP 2, 세션에 presentation_id 없으면 "/"로 리다이렉트)
/r/:id       → ReportScreen (STEP 3, ?token= 쿼리 필수)
```

### 2.8 공용 컴포넌트 (`components/`)

화면 특정 로직 없는 순수 UI만: `Button`, `ProgressBar`, `StepPill`, `Card`. 특정 feature 데이터를 몰라야 함(props로만 받음) — 재사용성 유지.

## 3. 구현 순서 제안

의존 관계상 이 순서가 자연스러움:

1. `api/` + `types/` (통신 계약부터 — 실제 배포된 백엔드로 바로 검증 가능)
2. `session/`
3. STEP 1 (`create/`) — 가장 단순, 전체 흐름의 시작점
4. STEP 2 (`upload/`) — presigned URL 업로드가 핵심 난이도
5. STEP 3 (`report/`) — 폴링 + 가장 복잡한 렌더링(리포트 스키마)
6. 공용 컴포넌트는 필요해지는 시점에 그때그때 분리(처음부터 만들지 않음)

## 4. 스코프 밖 (지금 안 함)

- 전역 상태 관리 라이브러리(Redux/Zustand) — 화면 3개, 공유 상태 적어서 불필요
- react-query 등 서버 상태 캐싱 라이브러리 — 폴링 로직이 단순해서 직접 구현이 더 가벼움
- 브라우저 녹음 UI — 화면설계.md §6 "남은 결정 사항"에 있음, 결정되면 `upload/` 안에 추가
