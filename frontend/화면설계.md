# 프론트엔드 화면 설계

> PTPT · 프론트 화면 흐름과 API 매핑.
> API 계약은 [`docs/API_명세서.md`](../docs/API_명세서.md) 참고. 여기는 그 계약을 화면으로 어떻게 풀지 정리.

---

## 0. 참고 디자인 대비 변경 사항

참고한 업로드 화면(3카드: PPT/오디오/스크립트)에서 두 가지를 바꿨습니다.

1. **스크립트를 파일 업로드(.txt/.docx)가 아니라 텍스트 입력창으로.**
   API의 `script` 필드는 파일이 아니라 텍스트 그대로 받습니다(`docs/API_명세서.md` §2.1). docx를 프론트에서 파싱하는 건 불필요한 복잡도라 textarea로 갑니다.

2. **스크립트를 업로드 화면(STEP 2)이 아니라 1단계(제목 입력) 화면으로 이동.**
   이유: `POST /api/presentations`는 `title`+`script`를 **한 번에** 받고, 이후 수정 엔드포인트가 없습니다. 그런데 업로드 화면에서 쓸 presigned URL(`slide_upload_url`/`audio_upload_url`)은 이 create 호출의 **응답**이라, create는 업로드 화면 진입 전에 이미 끝나 있어야 합니다. 즉 스크립트를 업로드 화면에 두면 그 시점엔 이미 create가 끝난 뒤라 반영할 방법이 없습니다. 그래서 스크립트는 제목과 같은 화면(1단계)에, 제목 아래 접힌 선택 항목으로 둡니다.

---

## 1. 전체 흐름 (3단계)

```
[1] 발표 정보 입력 → POST /api/presentations
        ↓ (presentation_id, presigned URL, result_token 획득)
[2] 자료 업로드 (PPT+오디오 필수) → S3 직접 PUT → POST /submit
        ↓ (status: PROCESSING)
[3] 분석 중 폴링 → GET (2~3초 간격) → DONE/FAILED 시 리포트 표시
```

세 화면 모두 URL/state에 `presentation_id`와 `result_token`을 들고 다녀야 합니다(2·3단계에서 `X-Result-Token` 헤더 필수). 새로고침에도 살아남게 `sessionStorage`(또는 URL 쿼리)에 저장 권장.

---

## 2. STEP 1 — 발표 정보 입력

**목적**: `POST /api/presentations` 호출에 필요한 정보 수집.

**구성 요소**
- 제목 입력 (필수, 텍스트)
- 대본 입력 (선택, 접힌 textarea — "펼치기" 형태. 안내 문구: "없어도 분석할 수 있어요. 있으면 대본과 실제 발화를 비교한 피드백을 더 받을 수 있어요.")
- "다음" 버튼 — 제목 없으면 비활성화

**동작**
1. "다음" 클릭 → `POST /api/presentations` body `{ title, script }` (script는 비어있으면 `null`로)
2. 응답의 `presentation_id`, `slide_upload_url`, `audio_upload_url`, `result_token`을 state/sessionStorage에 저장
3. STEP 2로 이동

**에러 처리**: 400(제목 누락 등) → 인라인 에러 메시지. 500 → 재시도 안내.

---

## 3. STEP 2 — 자료 업로드

참고 디자인의 카드 UI 그대로 활용 (PPT/오디오 2개만).

**구성 요소**
- PPT 업로드 카드 (필수) — 클릭/드래그, 성공 시 초록 테두리+체크, 실패 시 빨강 테두리
- 오디오 업로드 카드 (필수) — 파일 업로드 또는 녹음 UI(추후 결정), 성공/실패 표시는 PPT와 동일
- 진행 상태 바: "필수 항목 X/2 완료"
- "분석 시작하기" 버튼 — 2개 다 완료돼야 활성화

**동작**
1. 각 파일을 STEP 1에서 받아둔 `slide_upload_url`/`audio_upload_url`에 **직접 PUT** (백엔드를 거치지 않음 — presigned URL)
2. 오디오는 업로드 시점에 클라이언트에서 길이(ms) 측정해서 들고 있기 (`audio_duration_ms`, submit에 필요, 600000ms=10분 초과 시 업로드 단계에서 미리 경고 가능)
3. "분석 시작하기" 클릭 → `POST /api/presentations/{id}/submit` (헤더 `X-Result-Token`, body `{ audio_duration_ms }`)
4. 성공(202) → STEP 3으로 이동

**에러 처리**: presigned URL은 30분 후 만료 — 오래 머물다 업로드하면 S3에서 만료 에러 날 수 있음(재시도 시 STEP 1부터 다시 하거나, 재발급 방법은 추후 결정). submit 403(토큰 불일치)/400(길이 초과)은 인라인 표시.

---

## 4. STEP 3 — 분석 중 / 결과

**PROCESSING 상태**
- 로딩 UI (진행 애니메이션 등)
- `GET /api/presentations/{id}` (헤더 `X-Result-Token`)를 2~3초 간격으로 폴링
- 캐싱 이슈 없음 — CloudFront가 이 경로 캐싱 비활성화돼 있음

**DONE 상태**
- `report` 객체를 리포트 화면으로 렌더링:
  - `consistency` — 슬라이드 주장별 SUPPORTED/NOT_MENTIONED/NO_BASIS, 근거 발화 인용
  - `off_topic` — 주제 이탈 구간
  - `logic_gaps` — 논리 비약 구간
  - `delivery` — WPM, 침묵, 채움말, 성량 변화
  - `script_diff` — 대본 입력했을 때만(안 했으면 `null`)
- 이 시점에 처음으로 `result_url`을 사용자에게 노출하며 "이 링크 저장하세요, 3일 후 만료" 안내 (API_명세서 §2.1 참고)

**FAILED 상태**
- `error.code`/`error.message` 기반 에러 화면 (STT_FAILED/PPTX_PARSE_FAILED/AUDIO_NOT_FOUND/LLM_FAILED/TIMEOUT)
- 재시도 안내 — 단, 현재 백엔드 구현상 **분석 실패 시 오디오 원본이 삭제**돼서 재시도하려면 STEP 1부터 다시 시작해야 함 (알려진 이슈, 백엔드 쪽에서 논의 중)

**만료/권한 에러 (410/403)**
- 별도 화면: "만료되었습니다" / "접근 권한이 없습니다"

---

## 5. 화면 간 데이터 전달 요약

| 값 | 획득 시점 | 필요한 곳 |
|---|---|---|
| `presentation_id` | STEP 1 create 응답 | STEP 2 submit, STEP 3 조회 |
| `slide_upload_url` / `audio_upload_url` | STEP 1 create 응답 | STEP 2 업로드 |
| `result_token` | STEP 1 create 응답 | STEP 2 submit, STEP 3 조회, 결과 공유 URL |
| `audio_duration_ms` | STEP 2 업로드 시 클라이언트 측정 | STEP 2 submit |

---

## 6. 남은 결정 사항

- 오디오 입력: 파일 업로드만 지원할지, 브라우저 녹음 UI도 넣을지
- presigned URL 만료(30분) 대응: 오래 머문 경우 재발급 플로우
- 분석 실패 시 재시도 UX (백엔드의 오디오 삭제 이슈와 연결)

## 7. 전달력 기준 근거

분당 단어 수(WPM)
- 120~160: 적절 / 100~180(120~160 제외): 보통 / 그 외: 개선 필요
- 근거: National Communication Association 기준을 인용한 발표 코칭 자료(virtualspeech.com, thespeakerlab.com 등 다수)에서 "100 미만이면 청중이 지루해하고, 180 초과면 이해도가 떨어진다"는 수치를 가져옴.

채움말 횟수 (분당 기준으로 정규화)
- 분당 2회 이하: 적절 / 5회 이하: 보통 / 그 초과: 개선 필요
- 근거: Quantified Communications, Carleton University 커뮤니케이션 연구 — "평균 화자는 분당 5회, 전문 발표자는 분당 1~2회, 분당 10회 넘으면 확실히 거슬린다"는 자료.

긴 침묵 구간 (분당 기준)
- 분당 1개 이하: 적절 / 2개 이하: 보통 / 그 초과: 개선 필요
- 근거: 이 부분은 리서치로 못 찾았어요. ai-service가 "긴 침묵"을 1초(LONG_PAUSE_THRESHOLD_MS) 이상 공백으로정의하는데, TED 발표자들의 "분당 평균 5회 전략적 멈춤" 통계는 의도된 임팩트용 멈춤을 세는 거라 우리가 말하는 "어색한 공백"과 성격이 달라서 그대로 못 씀. 그래서잡은 기준이에요 — 정확한 근거는 없어요.

총 침묵 시간 (전체 길이 대비 비율)
- 15% 이하: 적절 / 25% 이하: 보통 / 그 초과: 개선 필요
- 근거: 이것도 리서치에서 직접적인 기준을 못 찾았어요. 일반적인 감각으로 잡은 수치예요 — 출처 없음.

성량 기복 (relative_std, 200ms 프레임 RMS 변동 계수)
- 등급 없음 — 값과 설명만 보여줌
- 근거: "변동계수가 클수록 성량 기복이 크다"구에서 확인됐고, 이 커스텀 지표(200ms RMS변동계수)에 대한 절대 기준값은 어디에도 없어서 등급을 안 매겼어요. ai-service 코드 주석에도 "절대 기준값은 실데이터로 보정 필요"라고 명시돼 있어요.
